# Lessons

Format: `[date] | what went wrong | rule to prevent it`

[2026-06-21] | Spent the first round of debugging a "cross-device sync broken" report entirely in application code, when the real root cause was Firestore's default test-mode security rules silently expiring 30 days after creation and denying all reads/writes | For any Firebase/Firestore sync or save issue, check the Rules tab first (test-mode expires 30 days after the database is created) before deep-diving into application code.

[2026-06-21] | Added a `touchedSinceLoadStart` guard ref to stop an async load from clobbering an in-flight local edit, but never cleared it after the load resolved — it ended up permanently blocking real-time updates for any key touched once, for the rest of the session | Any guard tied to an async window (load, debounce, etc.) must be explicitly cleared when that window closes, not just reset on the next outer trigger. Audit new guards for unbounded lifetime before shipping.

[2026-06-24] | Built a click-and-drag range-select for the new "No Phone Time" calendar feature and finalized the drag on `onMouseUp`/`onMouseLeave` of the day-column wrapper element. A fast/automated drag whose pointer left that element mid-gesture fired `onMouseLeave` and collapsed the selection to 1 slot before the real mouseup. | Any drag-to-select interaction must finalize on a `window`-level `mouseup` listener (added via `useEffect` while the drag is active, removed after), never on `onMouseUp`/`onMouseLeave` of the element being dragged over — the pointer routinely leaves that element mid-drag even in normal (non-automated) use.

[2026-07-20] | Spawned 4 parallel general-purpose subagents for the emoji→icon migration (one per file batch); all 4 died mid-task with "session limit" errors, and one had partially rewritten a section of `DailyLogPage.jsx` beyond its literal instructions (redesigning the habit-checkin row into a dropdown menu) before dying, which I almost missed by trusting my own pre-spawn grep as "current state" | After any batch of parallel subagents editing code returns/fails, re-grep the actual current file contents before continuing — don't assume "agent made zero progress" just because most of the diff looks unchanged; check every target file freshly. For large mechanical multi-file edits, doing them directly (with the mapping already fully decided) is often more reliable than spawning many heavy parallel agents that can each silently fail.

[2026-07-20] | This project's ESLint config includes the experimental React Compiler rules (`eslint-plugin-react-hooks` v6, e.g. `react-hooks/purity`, `react-hooks/static-components`). It falsely flagged a capitalized variable (`Icon`) as "defined but never used" when destructured directly in a `.map((...) => <Icon .../>)` arrow's parameter list and used as a JSX tag within that same single-expression body — even though it's genuinely used | When converting a data field to an `Icon` component consumed via `.map()`, destructure it in a block-bodied callback as `const Icon = item.Icon;` (matching this codebase's existing `statMeta.js` convention) rather than inline in the arrow's parameter list, to avoid tripping this rule.

[2026-07-20] | Converting several single emoji glyphs to `<Icon/> text` pairs (e.g. `✕ Cancel` → `<X/> Cancel`) rendered misaligned/uncentered in a few spots because the surrounding CSS class had no `display:flex` (a lone emoji glyph doesn't need flex to look centered; an icon+text pair does) | Whenever an emoji-only or bare-glyph UI element becomes icon+text (or an icon-only button), check its CSS class for `display:flex; align-items:center; gap` and add it if missing — this codebase's own icon+text convention (see `.wp-hero-cta`) already relies on it.

[2026-07-20] | Positioned the new Brain Dump page's empty-state hint at `top: 40%` intending to center it in the viewport, but it's a child of a `.bd-canvas` board deliberately taller than the viewport (`min-height: 3200px`) — 40% of that landed ~1280px down, invisible on page load without scrolling. Caught only via a Playwright screenshot, not by reading the CSS. | For any absolutely-positioned UI cue inside a board/canvas element that's intentionally taller than the viewport (scrollable freeform layouts), position it with a fixed pixel offset from the top, never a percentage of the element's own height — percentage centers within the full scrollable content, not what's actually visible. Screenshot new full-page layouts before calling them done; this class of bug doesn't show up in code review.

[2026-07-21] | Built a `ResizeObserver` to track a Brain Dump note's live rendered size (needed so connection lines stay attached to a text-driven variable height), seeding the initial measurement correctly via `getBoundingClientRect()` (border-box) at mount, but reading `entry.contentRect` (content-box — excludes padding/border) inside the observer callback itself. The observer's first delivery (which always fires once immediately after `.observe()`) silently overwrote the correct border-box size with a content-box one, permanently short by exactly the padding+border total (22px in this case) — a stable, non-transient wrong value, not a one-frame flash, so it read like a logic bug rather than a timing race until measured at multiple delays and found identical every time. | `ResizeObserver`'s `entry.contentRect` is always content-box, never border-box, regardless of the element's own `box-sizing`. If any other measurement of the same element (initial mount, `getBoundingClientRect()`, CSS positioning math) assumes border-box, use `entry.target.getBoundingClientRect()` inside the observer callback too rather than `entry.contentRect` — don't mix the two sizing models for the same tracked value.

[2026-07-22] | Redesigned WelcomePage with a `flex:1 1 auto` zone meant to consume leftover vertical space inside `.wp-layout` (a column flex container) so a live clock would center in the viewport. It silently sat at its `min-height` floor and never grew. Root cause: `.wp-layout`'s own `min-height:100%` requires its parent (`.wp-bg`) to have a genuinely *definite* height for the percentage to resolve — but `.wp-bg` itself only had `min-height:100%` (not `height`), and being a plain block (not a flex container), that percentage doesn't count as "definite" for its own children even though `.wp-bg` itself correctly resolves to 100vh as a flex item of `.content-container` one level up. A percentage-height chain that works for one link can silently break on the very next link if that link isn't also a flex item of a definite-height flex container. | Before relying on `flex-grow`/percentage-height to fill available space, verify every link in the ancestor chain is *itself* a flex item of a container with a genuinely definite height (or `display:flex` propagating it further) — don't assume a chain works just because the end result "looks full-height" for unrelated content. Verify with a real DOM inspection (`getBoundingClientRect()` in a Playwright script) that the box's rendered height actually changed, not just a screenshot glance.

[2026-07-22] | Same WelcomePage session: after fixing the flex-centering bug above, the background photo's watermark ("Apex Studios" text + logo) — previously hidden by the old design's diagonal dark-left/light-right overlay tuned for a left-heavy layout — bled through behind the new full-width-centered content. Iterated on the fix by eyeballing Playwright screenshots and judged several genuinely-effective opacity increases as "not dark enough," including one attempt that objectively hit ~90% black coverage by the alpha math. Wrote a pixel-luminance sampler (temporary `pngjs` dependency, decoded the actual screenshot PNG bytes) and found 97% of the region was already below luminance 20/255 — the fix had been working since an earlier iteration; the *rendered preview I was visually judging the screenshots through* was misleading me about actual contrast, not the CSS. | Don't trust visual judgment of subtle contrast/opacity from a rendered image preview alone, especially after several "still not dark enough" iterations in a row — that's a signal to switch to objective pixel sampling (decode the actual screenshot bytes and check luminance/alpha) rather than continuing to nudge values blindly. Also: when a layout changes from asymmetric (content concentrated in one region) to symmetric/centered, any background-image overlay tuned for the old asymmetry (directional gradients favoring the previously-content-heavy side) needs re-tuning too — check every region that previously had no content sitting on it, not just the new focal element.

[2026-07-23] | After verifying the Mentor→Claude migration with a temporary dev server, ran `pkill -f "vite"` to clean up — this killed every Vite process by name match, including two other dev server instances (ports 5173/5174) that were already running before this session started and weren't mine to stop. | Never `pkill -f` a broad process-name pattern to stop a dev server you started — `ps aux` first to see what's actually running, then kill the specific PID your own `npm run dev`/background launch reported (or use the tool's own background-process handle if one exists). A generic name match can silently take down processes another session or the user started.

[2026-07-23] | User reported a vague "black sticky section beneath the input bar" on the Calendar page. Spent a long time screenshotting every view/viewport/modal at various sizes trying to visually spot it (in an all-black dark theme, a dead-space bug and normal background look identical in a screenshot) before it occurred to me to just ask the user to right-click → Inspect Element and read back the highlighted class name — which instantly named the exact element (`.content-container`) and led straight to the real bug (`CalendarPage.css`'s `.cal-page` hard-coding `height: calc(100vh - 100px)`, a 100px dead-space leftover unique to that one file — every sibling page uses `height: 100%`). | For a "there's an empty/misplaced/wrong-colored box somewhere" UI report in a dark (or otherwise low-contrast) theme, don't burn cycles guessing-and-screenshotting blind — ask the user to Inspect Element and read back the class name early, before trying more than one or two screenshot guesses. It's a 10-second ask that turns a fuzzy visual bug into an exact selector. Also: once a specific DOM node is named, verify a suspected sizing bug with `getBoundingClientRect()` measurements (not just a screenshot glance) — the 100px gap was confirmed as an exact, reproducible number this way, both before and after the fix.

[2026-07-24] | During post-verification cleanup for the My Assistant redesign, ran `rm -f shoot_assistant.mjs shoot_assistant2.mjs check_pixel.mjs shoot_welcome.mjs tmp_verify_toggle.mjs welcome-test.html` in one batch — but only the first two were this session's own harness scripts; `check_pixel.mjs`, `shoot_welcome.mjs`, `tmp_verify_toggle.mjs`, and `welcome-test.html` were pre-existing untracked leftovers from earlier sessions (visible in `git status` at session start), and since they were untracked, `rm` deleted them with zero git recovery path. | Never glob-delete or batch-`rm` verification/harness scripts at session end without first checking each filename against the session's own file-creation history (or `git status` from session start) — only delete files this session actually created. If a cleanup command would touch a file that predates the session, stop and ask, even if the filename pattern (`shoot_*`, `tmp_*`, `*-test.html`) looks like disposable scratch work.

[2026-07-24] | Redesigned the My Assistant drawer using the app's purple `--ai-accent` token, reasoning from `tokens.css`'s own comment that purple is reserved for "AI-flavored features" — a reasonable-sounding rationale that turned out not to be what the user wanted. User immediately corrected: "should use the existing blue accent... not purple." | A token's own doc comment describing its *intended* scope is not the same as the user's actual preference for a *specific* feature — don't treat a codebase comment as license to skip checking with the user on a visible, subjective design choice (color/accent selection) that a plain design-token convention doesn't obviously force. When redesigning a highly visible UI surface's color language, the safer default is the color already used by the most similar/adjacent existing element (here: `FloatingAIBar`, the assistant's own entry point, already used blue) rather than a differently-scoped token whose comment merely permits an alternative.

[2026-07-25] | Built a mobile 2-column grid (`WelcomePage.css` `.wp-bottom-grid`) whose cells contain `white-space:nowrap` + ellipsis text (an existing, pre-change pattern). Verified "zero scroll" via `scrollHeight === clientHeight` on `.content-container`/`.wp-bg` and it passed — but a populated-data screenshot showed the second grid column (Goals/Priority tiles) missing entirely. Root cause: a grid item's default `min-width:auto` resolves to its content's min-content size, and a `nowrap` text node's min-content equals its full unwrapped line width — this silently forced the first column wide enough to fit the longest task/goal line, pushing column 2 off-screen. The scrollHeight check never caught it because the overflow was *horizontal*, absorbed by the page's own `overflow:hidden` safety net rather than producing a scrollbar. | The `scrollHeight === clientHeight` check only proves no *vertical* page scroll — it says nothing about horizontal min-content blowout inside a fixed-width grid/flex container. Whenever a grid or flex item contains `white-space:nowrap` (or otherwise-unwrapped) text relying on `overflow:hidden;text-overflow:ellipsis` to truncate, that item (and flex children down the chain, e.g. a `flex:1` text span inside a flex row) needs an explicit `min-width:0` — the ellipsis silently never engages otherwise, because the container just grows to fit instead of clipping. Always screenshot a heavily-populated data state (not just empty-state) for any layout claim like "fits without scrolling," since content-volume-dependent bugs like this one don't show up with placeholder/empty content.

[2026-09-09] | Wrote a new plan into `tasks/todo.md` with a `cat > tasks/todo.md <<'EOF'` heredoc, which truncated the file and destroyed ~495 lines of accumulated session history. Recoverable only because todo.md happened to be committed (`git show HEAD:tasks/todo.md`) — had it been dirty or untracked, the history would have been gone. | Never write to an append-style project log (`tasks/todo.md`, `tasks/lessons.md`, `memory/*.md`) with a truncating redirect (`>` or `cat > file <<EOF`). Use `>>` to append, or read-modify-write via a script that preserves existing content. Truncating redirects are for files you are creating for the first time only.

[2026-09-09] | Clamped a `position:fixed` hover card into the viewport using `el.offsetWidth`/`offsetHeight`, which round to whole pixels — the card's real height was 191.25px, so the clamp computed a top that let it overhang the bottom margin by 0.25px. Invisible by eye; only a numeric `boundingBox()` assertion caught it. | For any viewport-clamping / collision-avoidance positioning math, measure with `getBoundingClientRect()` (fractional), never `offsetWidth`/`offsetHeight` (integer-rounded). And assert the result numerically (`box.y + box.height <= viewportH - margin`) rather than eyeballing a screenshot — sub-pixel overhang never shows up visually.

[2026-09-09] | Wrote a "does the hover card follow grid scroll?" Playwright assertion against a block scrolled to the very bottom of the grid — the card was pinned at its viewport clamp floor, so it correctly didn't move, and the test read as a failure ("card dismissed on scroll") for the wrong reason. Also scrolled 120px past a 64px-tall block, which legitimately fired `mouseleave`. | When testing position-following behavior, pick a test subject in the *middle* of its range, away from any clamp/boundary that would mask the thing being measured, and keep the perturbation smaller than the element so the triggering hover state survives. A boundary-pinned element proves nothing about following.

[2026-09-09] | Marked a plan's checkboxes done in `tasks/todo.md` with a blanket `s.replace("- [ ] ", "- [x] ")` over the WHOLE file, to flip the 5 items in the section I had just written. It happened to be safe only because no other section still had an open box — had any older section carried unfinished work, I would have silently marked it complete, and a `- [x]` looks like history rather than damage, so nobody would have caught it. | Same family as the truncating-redirect lesson: on an append-style log (`tasks/todo.md`, `tasks/lessons.md`, `memory/*.md`), never apply a whole-file string replace to edit one section. Scope the edit to the section (split on its heading, transform that slice, rejoin) and then confirm with `git diff --stat` that the change is insertions-only — or, for a replace, that every changed line is one you meant to touch.

[2026-09-09] | Measured a newly opened mobile drawer's layout 300ms after the click and concluded the new footer chip fell outside the viewport — the drawer was still mid slide-in at `translateY(100%)`, so `getBoundingClientRect()` returned its pre-animation position, not its resting one. Nearly "fixed" a layout bug that did not exist. | Before asserting anything about a freshly mounted/opened element's geometry, settle its animations first — `el.getAnimations().forEach(a => a.finish())` (synchronous, and works even when the browser pane is hidden and rAF is throttled). Do NOT `await a.finished` in a hidden/background pane: rendering is paused there, the promise never settles, and the call just times out. A fixed `setTimeout` is not a substitute — it races the animation instead of waiting for it.

[2026-10-16] | Built a My Assistant nudge whose "Mark it" button navigates to Home's commitment tile, but keyed the nudge's "pending" check off `commitmentArchive` alone, while the tile keys off `logs[yesterday].commitment` + the archive record. The nudge could therefore send the user to a tile with no buttons on it. Unit tests passed because they were seeded the way my new code reads data; it was only caught by seeding the browser the way the real flow writes it. | When a new surface links to an existing UI action, reuse that UI's exact visibility condition (read the target component first; extract and share the predicate if practical), and test the hand-off end to end with data shaped the way the real write path produces it.

[2026-10-16] | Diffed ESLint output before/after my change to prove "no new lint" with `F="a.js b.js"; npx eslint -f unix $F … > before.txt`. In zsh an unquoted `$F` does not word-split, so ESLint got one nonexistent path and (with stderr discarded) both outputs were empty; the diff "passed" vacuously. Only noticed because a known new warning was missing. Redone properly, it found a real new error. | Any "before vs after is identical" check must also assert the outputs are non-empty (print `wc -l`) before trusting an empty diff. In this zsh shell, pass file lists as arrays (`F=(a b)`; `$F`) or `${=F}`, and never discard stderr on the command producing the evidence.

[2026-10-16] | Twice during the Plan My Day UI test, a click "didn't register" by the screenshot (debrief chip, Start focus), but a DOM read right after showed the click had worked; the Browser-pane screenshot was a frame behind. I nearly started debugging a non-bug. Separately, the app's Google sign-in gate blocked UI testing of the real App. | When a screenshot says an interaction failed, confirm with a DOM read (`elementFromPoint`, class/state check) before treating it as a bug. To UI-test the real App behind AuthGate, run a second Vite server from a scratchpad config (`--configLoader native`, `root` = project, a `resolveId` plugin swapping `context/AuthContext` for a stub, `transformIndexHtml` pointing at a scratchpad entry that seeds localStorage and fakes Gemini at `window.fetch`). That adds no files to the repo and tests the real components.
